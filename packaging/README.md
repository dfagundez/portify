# Packaging

How Portify reaches a package manager, and what is automated.

| Channel | Where the manifest lives | Updated by |
|---|---|---|
| Scoop | [`bucket/portify.json`](../bucket/portify.json) — this repository *is* the bucket | Automatically, on release |
| winget | [`packaging/winget/`](winget/) | Automatically here, then a manual PR to Microsoft |
| crates.io | the crates' own `Cargo.toml` | `cargo publish`, by hand |

## Scoop

Scoop reads manifests straight out of a git repository, and a repository with a
`bucket/` directory is a valid bucket. So Portify does not need a second repo:

```powershell
scoop bucket add portify https://github.com/dfagundez/portify
scoop install portify
```

Once [`bucket/portify.json`](../bucket/portify.json) lands on `main`, every user
picks it up on their next `scoop update`. Nothing to submit and nobody to wait
for.

## winget

winget only reads manifests from
[`microsoft/winget-pkgs`](https://github.com/microsoft/winget-pkgs). Keeping a
copy here does not publish anything — it means the files are versioned,
reviewable and generated by the same script as everything else, so the pull
request is a copy rather than a fresh act of authorship each time.

To submit a version:

1. Fork `microsoft/winget-pkgs`.
2. Copy the three files into `manifests/d/DiegoFagundez/Portify/<version>/`.
3. Open a pull request titled `New version: DiegoFagundez.Portify version <version>`.

Their CI validates the schema, downloads the installer, checks the hash, and
installs it in a sandbox. A first submission is reviewed by a human; later
version bumps are usually merged by the bot within a few hours.

The manifests describe the **NSIS installer only**, not the `.msi`. Both are
published, but the NSIS build is the one installed and tested by hand, it
installs per-user so winget never has to elevate, and one installer per package
is one fewer thing to keep in sync.

## Two scripts

```bash
node scripts/update-packaging.mjs v0.2.0   # rewrite the manifests for a release
node scripts/check-packaging.mjs           # verify they match the published files
```

`update-packaging` reads the **published** release from the GitHub API — a draft
release has no downloadable assets, so there would be nothing to checksum — then
fetches each artefact, computes its SHA-256, and rewrites the four files.
Re-running it for the current version changes nothing, which is what makes it
safe to run whenever you are unsure.

`check-packaging` runs in CI on every push. It re-downloads whatever the
manifests point at and fails if a checksum disagrees, or if the version was
bumped without the URL following it — a half-finished release bump is the
failure that would otherwise be discovered by a stranger whose `scoop install`
hands them the previous month's binary.

Both are driven by
[`.github/workflows/packaging.yml`](../.github/workflows/packaging.yml), which
runs when a release is published.

## crates.io

```bash
cargo publish -p portify-core     # first: the CLI depends on it
cargo publish -p portify-cli      # once the index has the core
```

Order matters — crates.io rejects a crate whose dependency it has never heard
of, so `portify-cli` cannot go first.

`portify` is taken there by an unrelated HTTPS/SVCB library, so the CLI is
published as [`portify-cli`](https://crates.io/crates/portify-cli). The binary
it installs is still named `portify`.

`portify-app` is marked `publish = false`. It was publishable by default, and
`generate_context!` embeds `app/dist` at compile time — a published copy would
fail to build for everyone who downloaded it.

The `portify-core` README's examples are compiled as doctests (see the
`Readme` struct in its `lib.rs`), because the crates.io landing page is the
first code anyone reads and the last anyone checks.

## Published artefacts are immutable

Not a principle — a rule the release workflow now enforces, because it was
learned the hard way.

Force-pushing the `v0.1.0` tag (for an unrelated history rewrite) re-triggered
`release.yml`, which rebuilt all ten binaries and replaced the release assets.
Same source tree, different bytes, different checksums. Everything downstream
that had already recorded a checksum was instantly wrong:

- **Scoop** healed itself — `packaging.yml` recomputed and committed the new
  hash. This is exactly the rot the automation exists to catch, and it caught
  it.
- **winget did not**, and could not. The submission to `microsoft/winget-pkgs`
  had passed validation against the old installer. Merged as-is, every
  `winget install` would have failed its hash check. It had to be corrected by
  hand, on a public PR, after a reviewer had already looked at it.

So `release.yml` starts with a `guard` job that refuses to build when the tag
already has a **published** release. Draft releases still rebuild freely —
those are the ones still being assembled. To genuinely replace a published
release, delete it first; the refusal should be a deliberate step, not
something a stray `git push --force` does on your behalf.

## Not done yet

- **Homebrew.** A tap has to be its own repository (`homebrew-portify`), and
  Portify has never been run on a Mac. Shipping a formula for a platform nobody
  has tested would be selling something unverified.
- **Signed installers.** Tracked in
  [#4](https://github.com/dfagundez/portify/issues/4). Until then both winget
  and a direct download raise a SmartScreen warning.
